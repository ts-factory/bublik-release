Release v2.19.1

October 26, 2026 · 28 min read
Kostromin Danil
Bublik UI Maintainer
Rybchenko Natalia
Bublik Backend Maintainer

We're excited to announce Bublik v2.19.1!
This release adds result classification. You can explain a failure once by attaching it to an issue, and Bublik matches the same failure in future runs. Sign-in now happens in a dialog on the page you're on, and the sidebar gets an account menu with a dark mode and Beta features. History search now runs on the server

What's New​

Result Classification
Select failed results, classify them under a new or existing issue, and decide whether they still count as unexpected. The rules carry the classification over to future runs. Issues, rules and their results each have their own page.

Sign In Without Leaving the Page
When an action needs an account, Bublik opens a login dialog and then finishes what you started. The sidebar's Settings item becomes an account menu.

Dark Mode and Beta Features
Choose System, Light or Dark in the account menu. Try experimental features from the new Beta menu.

Highlights​

Result Classification​

A run often fails in ways the team already knows about: a known product bug, a flaky test.
Until now every run reported them again as unexpected.
With classification you explain a failure once and Bublik remembers it.

There are three new terms:

  • Issue: the reason results failed, such as a bug, a flaky test or an environment problem. It can link to your bug tracker, for example JIRA-145.
  • Rule: the results of one test that belong to the issue. A rule matches the test path and, optionally, parameters, verdicts and tags.
  • Stamp: the mark a rule leaves on a matching result. Stamps are added when a run is imported, when you classify, or when you click Apply Rules.

Each rule has a category, and the category sets the default disposition, which decides whether the stamped results still count:

CategoryBadgeDefault disposition
Product defectDEFECTUnexpected
Test/automation bugTEST BUGExpected
Environment / infraENVExpected
Known issueKNOWNExpected
Flaky / intermittentFLAKYExpected
To investigateINVESTIGATEMarked
info

Viewing classifications is public.
Classifying results, applying rules and editing issues and rules require sign-in.
To allow this without sign-in, add manage_issues to the project's NOT_PERMISSION_REQUIRED_ACTIONS.

1. See What Is Already Explained​

Open a run and expand a test.
Every result that a rule matched shows its stamps under the verdicts: the issue key and the category.

  1. Stamps. Each line is one issue. The key links to the issue in your tracker. Here every ping failure is matched by a flaky issue (#21) and by a product defect (JIRA-145).
  2. Counts follow the disposition. The flaky rule marks these failures as expected, so all 8 move to Expected → Failed. The run no longer reports them as new problems.
  3. Classification filter. Show only untriaged results, or only results with a particular effect, to find what still needs attention.

2. Classify New Failures​

Click a failed result row to select it. Click more rows, even rows of other tests, to classify them together.

  1. Select rows by clicking them. Click a row again to deselect it.
  2. Classify N opens the Classify drawer for the selected results.
  3. The selection pill stays at the bottom of the page while you scroll and reopens the list of selected results.

The selection belongs to the run you made it in. It is still there when you come back from a result's log, but another run starts with nothing selected.

The Classify drawer has three sections:

  1. Issue. Record a New issue with a title, tracker and bug key, or pick an Existing issue.
    Pasting a full reference into Bug Key fills in the tracker and the key for you.
  2. Classification. Choose one or more categories. The disposition follows the category (see the table above), and you can override it. Each category creates its own rule.
  3. Apply to. This + future matching runs creates rules, so the same failure is stamped automatically when future runs are imported. Just this result stamps only the selected results and creates no rule.
  4. Match scope. Choose which future results the rule matches. The path is always matched. Parameters, verdicts and tags are pre-filled from the selected results; remove values to make the rule broader, or clear a field to stop matching on it. How matching works explains each field.
tip

When you create a rule for future runs, Bublik stamps only the results you selected. To stamp the other matching results in the current run, click Apply Rules on the run page.

3. Review the Run's Issues​

Each run now has an Issues page. It lists every issue that stamped at least one of the run's results, together with the number of results it stamped.

  1. Run → Issues in the sidebar shows how many open issues the run has. You can also open it with the Issues button in the run header.
  2. Actionable and Triaged set the Category filter with one click. Actionable covers to investigate, product defects and test bugs. Triaged covers environment, flaky and known issues.
  3. Apply Rules runs all active rules against the run's results again. Use it after you add or edit rules. Inactive rules and rules of closed issues are skipped. Apply Rules is also on the log and measurements pages.

4. Manage Issues and Rules​

Issues is a new top-level sidebar section. It lists the issues of all projects, grouped by project.

  1. Issues and Rules in the sidebar list all issues and all rules. The badge shows the number of open issues.
  2. Key. The issue's tracker key. Issues without a key show their ID, such as #21.
  3. Rules state. The number of active rules out of the total. An issue can also show No rules, No active rules or Deactivated.
  4. Actionable / Triaged presets, as on the run issues page. Search, State, Category, Rules and the sort order are kept in the URL, so you can share a filtered list.
  5. New Issue records an issue before anything fails, for example a bug that's already known.

Click an issue to open its page:

  1. The sidebar's Issue entry shows the issue key. Its submenu opens the issue's Results and Rules, with their counts.
  2. Close closes the issue and deactivates its rules. Suppressed results count as unexpected again. Reopening an issue does not reactivate its rules. Turn them back on one by one.
  3. Results lists every result the issue stamped, across all runs, with links to the run, log and history.
  4. Match scope shows what each rule matches on. Edit a rule to change its disposition, parameters, verdicts or tags, or to deactivate it.
  5. New Rule adds a rule to this issue without classifying a result first.

5. Follow an Issue in History​

History can now filter by classification. Open Edit Search and scroll to the new Classification section:

  1. Issue. Show only the results stamped by one issue.
  2. Triage state. Untriaged shows results that no rule has stamped. Triaged shows results that are already explained.
  3. Category. Show only results stamped under the selected categories.

The filters are written to the URL, so a filtered History page can be shared:

  1. The Issue filter shows the issue's key and title.
  2. Each result shows its stamps, as on the run page.

The search form's parameter, tag, label, branch and revision fields now suggest values that exist in the project.

Sign-In Dialog and Account Menu​

Signing in is now done in a dialog instead of on a separate page.

  • Signing in. If your session is missing or has expired, Bublik shows a login dialog and repeats the request after you sign in. You stay on the same page.
  • Run page. When you're signed out, adding or editing notes and marking a run as compromised show a "Log in to …" tooltip. Clicking opens the login dialog. These actions used to fail with an error toast. Error toasts now show the reason the server gave.
  • Protected pages. Chat requires sign-in. Admin → Users and Admin → Analytics are available to administrators only.
  • Account menu. The sidebar's Settings item is replaced by an account row with your avatar, name and email. It opens a menu with the settings sections and Sign Out. When you're signed out, it shows a Sign In button.
  • Signing out keeps the sidebar state and the selected project. If you're on a public page, you stay on it.

  1. The dialog says which action needs an account. Here a signed-out user clicked Classify. After signing in, Bublik continues with the classification.

Dark Mode and Beta Features​

  1. Appearance. Switch between System, Light and Dark right in the account menu, or under Settings → Appearance. The choice is saved in your browser, and Light is the default. Tables, charts, code editors and logs all follow the theme.
  2. Beta. A list of experimental features, each with an on/off switch. The number on the Beta item shows how many features are available, and new ones are marked NEW. The same switches are under Settings → Beta.

The first Beta feature is Dashboard Grid Layout. It lays out the dashboard table as a grid: numbers are right-aligned, short values are never cut off, and headers stay at the top while you scroll.

Server-Side History Search​

The History substring filter used to match only the rows on the current page. Matches on other pages were missing, and counts and pagination ignored the filter. The search now runs on the server across all results:

  1. Type in Substring filter and press Submit. The search matches tags, metadata shown on the page, parameters in name=value form, verdicts and the result type. It is case-insensitive.
  2. The search is saved in the URL as ?search=, so it survives a reload and is included when you share a link. Reset Filter clears it.

Counts, pagination, measurements and the legend now reflect the search.

User Management​

Admin → Users shows each user's Status (Pending, Active or Deactivated) and the date they joined. Deactivated users can now be reactivated, so deactivation is no longer permanent. If a user action fails, the error message shows the reason the server gave.

Account security is tightened as well:

  • Changing your password now requires the current one. Changing or resetting a password signs out the user's other sessions.
  • Deactivating a user ends their existing sessions right away.
  • Password reset links work only for the user they were sent to, and deactivated users can no longer reset their password or get reactivated by an old verification link.
  • Administrators can't deactivate themselves or the system user, and the system user is no longer listed.
  • If an email can't be sent, the error says so instead of reporting an unexpected server error.

Smaller Improvements​

  • Sidebar. The Log entry moved under Run, next to Details, with buttons to switch the log layout. The Run entry shows the run ID, and the navigation scrolls with a thin scrollbar that doesn't take up width.
  • Dashboard. The Auto reload setting is kept when you reload the page. Runs with hundreds of iterations no longer shrink their result strip to nothing.
  • The version label in the sidebar links to the release notes for that version.
  • In the run table, Objective and Notes come right after the tree by default instead of at the end, unless the project's RUN_STATS_COLUMNS_DEFAULT sets their position. Column orders you've saved are kept.
  • The Import events table no longer re-renders four times a second while auto-refresh is on.
  • Short URLs that failed to open or led to the wrong page now open the page that was shortened.
  • API. A JSON request body that repeats a key is now rejected with 400, and an invalid project ID returns a clear error instead of a server error.

Admin Section​

Backend Update​

warning

The server_packages deployment step requires root rights. If you don't have root access, you must manually install the python3-venv package, which is now used instead of python3-virtualenv to build the virtual environment. If ENV_PYTHON points to a non-default Python, install the matching python3.X-venv package instead.

  1. cd bublik
  2. git remote update
  3. git checkout v2.19.1
  4. ./scripts/deploy --steps server_packages general_conf pip_requirements django_settings migrate_db run_services
warning

EMAIL_USE_TLS now defaults to false, but existing configurations may still contain "EMAIL_USE_TLS": true. Check it: use false for a local mail agent on localhost and true for an external SMTP server that requires STARTTLS.

# 3. Pull the latest docker image
task pull

# 4. Start the docker container
task up
